# Review de inconsistências — 2026-11-02

Review do código, da documentação e das skills na versão 0.10.3 mais o commit
`ed27465` (helpers dentro do `banking`). Nada aqui foi corrigido ainda: este
documento é a lista de trabalho.

Cada item traz onde está, o que acontece e a correção sugerida. **Confirmado**
quer dizer reproduzido com o binário (`--dry-run`, nunca chamadas reais que
criam dados) ou lido no código; **provável** quer dizer deduzido do código sem
reprodução.

Ordem sugerida: seções 1 e 2 (bugs e segurança), depois a 3, depois a 4.

---

## 1. Bugs com efeito real

### 1.1 `+cobrar` manda um corpo que a API rejeita — confirmado
- `crates/kobana-cli/src/helpers/pix.rs:75` grava `payer.document`; o schema
  `v2_pix` de `specs/banking-v2.json` chama o campo `payer.document_number`.
- O schema exige `expire_at` (`required: amount, pix_account_uid, expire_at`) e
  o helper não tem flag de vencimento.
- O schema exige `name` e `document_number` juntos em `payer`; o helper aceita
  `--nome` ou `--cpf-cnpj` sozinhos.
- **Correção:** renomear para `document_number`, adicionar `--vencimento`
  obrigatório e exigir `--nome` com `--cpf-cnpj`.

### 1.2 Helpers transformam número inválido em 0 — confirmado
- `helpers/boleto.rs:53-65` e `helpers/pix.rs:52-56` usam
  `.parse().unwrap_or(0.0)` / `.unwrap_or(0)`.
- `kobana banking +emitir --valor 150,50 --carteira zz --dry-run` gera
  `"amount": 0.0, "bank_billet_account_id": 0` e sai com 0. Um usuário que
  digita vírgula decimal emite um boleto de R$ 0,00.
- O caminho dinâmico rejeita entrada inválida com código 3.
- **Correção:** devolver `KobanaError::Validation` quando o parse falhar.

### 1.3 Parâmetros de rota pegam o valor de outro parâmetro — confirmado
- `executor.rs:305-313` usa `uid`/`id` como reserva para qualquer `*_uid`/`*_id`.
- `kobana banking charge pix commands get --params '{"uid":"CMD"}' --dry-run`
  monta `/v2/charge/pix/CMD/commands/CMD` (o id do comando no lugar do pix).
- `dashboards entities records get --params '{"id":"ENTITY_ID"}'` monta
  `/v1/entities/ENTITY_ID/records/ENTITY_ID`. O README (`:526`) e a skill
  `kobana-dashboards` (`:81`) usam esse exemplo.
- Só o nome real é removido da query (`executor.rs:130-137`):
  `charge pix cancel --params '{"uid":"P1"}'` também manda `?uid=P1`.
- **Correção:** usar a reserva só quando ela não for ela própria um parâmetro
  do template, e remover da query a chave que foi usada.

### 1.4 `validate_identifier` deixa passar `/` e `..` — confirmado
- `crates/kobana/src/validate.rs:15` só barra a sequência `"../"`.
- `{"id":"1/cancel"}` em `bank-billets get` vira `GET /v1/bank_billets/1/cancel`,
  outra rota. `{"id":".."}` vira `/v1/bank_billets/..`, que o reqwest normaliza
  para `/v1/`.
- O AGENTS.md diz que a validação rejeita path traversal.
- **Correção:** rejeitar `/`, `\`, `?`, `#` e os valores `.` e `..`.

### 1.5 `+cancelar-lote` não valida os ids — confirmado
- `helpers/boleto.rs:150,167` monta `/v1/bank_billets/{id}/cancel` direto.
- `--ids "../../v2/charge/pix/x,,a?b"` é aceito, inclusive o id vazio.
- **Correção:** `validate_identifier(id, "id")` em cada id e descartar vazios.

### 1.6 `+cancelar-lote` sai com 0 mesmo quando tudo falha — confirmado
- `helpers/boleto.rs:184-195` junta os erros no array de saída e devolve `Ok(())`.
- O caminho dinâmico sai com 1 em erro de API; scripts e agentes não percebem
  a falha.
- **Correção:** sair com erro de API quando algum item falhar.

### 1.7 Logout apaga a chave de criptografia de todos os diretórios — confirmado
- `credential_store.rs:147-150`: quando `saved_credential_files()` está vazio,
  apaga a chave do keyring. A busca olha só `config::config_dir()`, mas a
  entrada do keyring (`kobana-cli` / `encryption-key`) é global.
- `KOBANA_CONFIG_DIR=/tmp/x kobana billing auth logout` não acha nada em
  `/tmp/x` e apaga a chave; as credenciais em `~/Library/Application Support/kobana`
  ficam impossíveis de decifrar.
- O comentário diz que a chave sai com a última credencial, mas um `.key`
  local nunca é apagado.
- Gravar e ler preferem o keyring a um `.key` existente (`:263`, `:291`): um
  diretório cifrado com `.key` fica ilegível quando aparece uma chave no keyring.
- **Correção:** separar a entrada do keyring por diretório (ex.: hash do
  diretório no `user`) ou nunca apagá-la; preferir o `.key` quando ele existir.

### 1.8 `auth login --verbose` imprime os tokens — confirmado
- `oauth.rs:1043-1053` imprime o corpo da resposta do token inteiro, com
  `access_token` e `refresh_token`. Na requisição o código já mascara `code`,
  `code_verifier` e `client_secret`.
- Logs de CI com `--verbose` vazam os tokens.
- **Correção:** mascarar `access_token`, `refresh_token` e `id_token` no corpo.

### 1.9 `KOBANA_ENVIRONMENT` inválido vira produção — confirmado
- `config.rs:49-54`: `Some(_) => Environment::Production`. O `--env` tem
  `PossibleValuesParser`; a variável não.
- `KOBANA_ENVIRONMENT=sandbx` manda testes e logins para produção.
- **Correção:** erro para valores desconhecidos.

### 1.10 `kobana --json '{}' update` dá panic — confirmado
- O `--json` global recebe valor; o `update` define outro `--json` com o mesmo
  id como `SetTrue` (`commands.rs:379`). `main.rs:82` faz `get_flag("json")` e
  dá panic ("Mismatch between definition and access of `json`").
- **Correção:** outro id para a flag do `update`, ou declarar o conflito.

### 1.11 `--output-format` inválido só é pego depois da requisição — confirmado
- `formatter.rs:15` é a única checagem e roda depois de `client.execute`
  (`executor.rs:195,218`). `--output-format xml` num POST cria o registro e
  depois sai com 3.
- **Correção:** `PossibleValuesParser(["json","table","csv"])` em
  `commands.rs:224`.

## 2. Autenticação

### 2.1 `KOBANA_CREDENTIALS_FILE` vale para todos os produtos — confirmado
- `auth.rs:68-70`, `auth_commands.rs:425-430`: os campos `product` e
  `environment` do arquivo são ignorados.
- Um arquivo com token do banking faz `billing auth status` dizer
  `authenticated: true`, e `billing <cmd>` mandaria o token do banking. O
  `--env` também é ignorado.
- Contradiz o AGENTS.md ("um token serve a um produto") e o motivo da remoção
  do `KOBANA_TOKEN` no CHANGELOG 0.10.0.
- **Correção:** aceitar o arquivo só quando `product` (e `environment`) baterem,
  ou trocar por `KOBANA_<PRODUTO>_CREDENTIALS_FILE`.

### 2.2 `auth export` segue outra prioridade e não renova — confirmado
- `auth_commands.rs:456-486`: ordem variável de ambiente → salvo; o
  `resolve_token` e o `status` usam ambiente → arquivo → salvo.
- Com o arquivo definido e nada salvo, `status` diz autenticado e `export`
  falha com "No saved credentials found", sem a dica de `not_configured_for`.
- `export` imprime o `access_token` vencido como está; o `resolve_token`
  renovaria.
- No ramo da variável de ambiente, `"token_type": "Bearer"` é fixo.
- **Correção:** montar o `export` sobre um resolvedor comum que devolve a
  origem do token.

### 2.3 `auth status` esconde erros e afirma demais — confirmado
- `auth_commands.rs:425-430, 441`: qualquer erro vira `authenticated: false`
  com "nenhuma autenticação configurada… rode login". Um `.enc` corrompido ou
  impossível de decifrar mostra isso, enquanto o `export` diz "falha ao
  decifrar".
- `KOBANA_CREDENTIALS_FILE=/nao/existe` dá `authenticated: true`, caso em que o
  `resolve_token` falha.
- **Correção:** "não configurado" só quando `has_credentials` for falso; outros
  erros aparecem. Validar o arquivo como `read_credentials_file` faz.

### 2.4 `--client-secret` e `KOBANA_CLIENT_SECRET` fora do prometido — confirmado
- O help diz "só no fluxo Client Credentials, no banking". O código só usa
  client credentials quando os dois flags vêm juntos
  (`auth_commands.rs:268-286, 323`); `--client-secret` sozinho, ou os dois por
  variável de ambiente, vai para o authorization code com secret, em qualquer
  produto.
- `exchange_code` manda o `client_secret`; `refresh_token`
  (`oauth.rs:917-934`) não manda e o secret não é salvo. Um cliente
  confidencial nunca renova e cai em "expirou… rode login".
- `refresh_token` e o client credentials usam `reqwest::Client::new()`
  (`oauth.rs:880, 934`), sem User-Agent, Accept nem timeout; `exchange_code`
  e `fetch_json` definem esses três.
- **Correção:** tratar as variáveis como os flags na escolha do fluxo (ou
  recusar secret fora do client credentials) e usar um único construtor de
  cliente HTTP.

### 2.5 Renovação concorrente — provável
- `auth.rs:82-106`: sem trava entre carregar, renovar e salvar. Dois comandos
  em paralelo com o token vencido gastam o mesmo refresh token; com rotação ou
  detecção de reuso, o segundo falha e a família pode ser revogada.
- **Correção:** trava de arquivo em volta da renovação, relendo as credenciais
  depois de obtê-la.

### 2.6 Ambiente sem suporte dá a dica errada — confirmado
- `auth.rs:74-75`: `kadu auth status --env sandbox` e os comandos do kadu dizem
  "rode 'kobana kadu auth login'"; o login então falha com "kadu não tem login
  pela Conta Kobana em sandbox".
- **Correção:** checar `oauth_resource(env)` / `base_url(env)` antes de
  `not_configured_for`.

### 2.7 Dry-run resolve o token por completo — confirmado
- `main.rs:110-114, 139-145`: o comentário diz "For dry-run, we don't need
  auth", mas `resolve_token` roda, pode renovar pela rede, regravar o arquivo de
  credenciais e esconder erros de decifração com `unwrap_or_default()`.
- **Correção:** no dry-run, usar só o token da variável ou o salvo, sem renovar;
  ou corrigir o comentário.

### 2.8 Menores
- `product.rs:56-57`: o comentário de `OauthHosts` diz "`None` quando o servidor
  de autorização não tem resource para o ambiente", mas
  `kobana-app/config/oauth_resources.yml` tem resources de sandbox para inbox e
  kadu, que o CLI deixa `None`. Reescrever como "`None` quando o CLI não tem host
  nesse ambiente".
- `clap_i18n.rs:27`: o comentário ainda usa `kobana auth login [OPÇÕES]` como
  exemplo.
- `TokenSource::CredentialsFile(String)`: o `String` nunca é lido.
- `save_key_to_file` e `save_credentials` gravam e só depois aplicam `0600`; o
  `.key` em texto puro fica legível pela umask por um instante.

Sem achados: variantes pt/en/es concordam; nenhum código lê `KOBANA_TOKEN`;
state, PKCE e `resource` estão corretos em authorize, exchange e refresh.

## 3. Comandos gerados da spec e execução

### 3.1 Rotas de listagem somem — confirmado
- `/v2/charge/pix/{pix_uid}/commands` e `/v2/charge/pix/{pix_uid}/commands/{uid}`
  viram um único `get`; a listagem fica inacessível.
- O mesmo em `GET /v2/financial/accounts/{uid}/commands` e em
  `GET /v1/imports/{collection_name}/{id}` (o `get` atual é a listagem).
- As skills `kobana-charge:46`, `kobana-financial:37` e `kobana-v1:148-151`
  documentam o `list` que falta.
- **Correção:** na derivação de nomes de métodos, um GET sem parâmetro final de
  id deve virar `list` mesmo quando o recurso pai tem id na rota.

### 3.2 Helpers ignoram as opções globais — confirmado
- Os helpers imprimem `to_string_pretty(&response.body)` direto: `--output-format`,
  `--fields`, `--output` e `--verbose` não fazem nada; `--idempotency-key` é
  ignorado (sempre UUID novo); `--params`/`--json` são descartados. Essas opções
  aparecem no `--help` dos helpers.
- O dry-run dos helpers tem outro formato: `+cancelar-lote` mostra
  `{"action":"cancel_billets",…}` sem método nem URL; os outros não têm
  `headers`, `idempotency_key` nem `content_type`.
- **Correção:** passar os helpers pela saída e pelo dry-run do executor.

### 3.3 `--page-all` ignora `--output` — confirmado
- `paginate_all` (`pagination.rs:46`) não recebe o caminho de saída; tudo vai
  para a saída padrão.
- **Correção:** repassar `output_path`.

### 3.4 Paginação para cedo com `per_page` em string — provável
- `pagination.rs:65` lê com `.as_u64()`. Com `{"per_page":"20"}`, compara com o
  padrão 50 e para depois da primeira página.
- **Correção:** aceitar também string.

### 3.5 `kobana update` não confere o binário — confirmado
- `update.rs:323-398` instala sem checar SHA-256; `scripts/install.sh:247-269`
  confere o `digest` publicado pelo GitHub.
- **Correção:** comparar com o `digest` do asset antes do rename.

### 3.6 Código de saída 2 com dois significados — confirmado
- `clap_i18n.rs:162` sai com 2 em erro de uso; `ExitCode::AuthError = 2`
  (`error.rs:10`).
- `kobana help banking nope` devolve `Validation` (3, JSON na saída padrão);
  `kobana banking nope` sai com 2 no stderr.
- **Correção:** código próprio (ou 3) para erro de uso e o mesmo tratamento no
  `help` de comando desconhecido.

### 3.7 `--lang` aceita qualquer valor — confirmado
- `commands.rs:285`: `--lang fr` vira inglês sem aviso. O `--env` valida.
- **Correção:** valores possíveis `pt`, `en`, `es`.

### 3.8 Comentários desatualizados e código morto — confirmado
- `crates/kobana/src/client.rs:146-148`: "Products behind mTLS (inbox) require
  this"; o AGENTS.md diz que o inbox não usa mais mTLS.
- `crates/kobana/src/i18n.rs:5`: descreve a detecção de idioma sem o `--lang`.
- `formatter.rs:34`: "If there's a data wrapper, filter inside it" no ramo que só
  clona.
- `helpers/mod.rs:14`: `#[allow(dead_code)]` em `about()`, que é usado.
- `executor.rs:15`: parâmetro `_method_matches` sem uso.

Sem achados: todas as mensagens têm pt/en/es e concordam (a única diferença é
"unrecognized command" vs "unrecognized subcommand" no inglês); as linhas de uso
dos helpers dizem `kobana banking +verb`; nenhum produto é tratado de forma
diferente sem motivo.
